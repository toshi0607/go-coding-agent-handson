# go-coding-agent-handson

Zenn本「ミニClaude CodeをGoで実装して学ぶ コーディングエージェントのしくみ」の教材リポジトリです。

約2,000行のGoコードで、コーディングエージェントの中核機能をひととおり備えたミニエージェントを実装します。エージェントの正体は「LLM呼び出し → ツール実行 → 結果を返して再呼び出し」のループであり、このリポジトリはそのループを隠さず全部見せることを目的にしています。

## 構成

```
final/          完成形のミニコーディングエージェント
├── main.go       部品の組み立てとREPL
├── agent/        エージェントループ本体 + サブエージェント(Task tool)
├── llm/          LLM呼び出しの境界(実API / 録画リプレイ)
├── tools/        read_file, list_files, edit_file, bash + 作業ディレクトリの封じ込め
├── permission/   承認フロー(allowlist)
├── prompt/       システムプロンプト + CLAUDE.md読み込み
├── skill/        スキル(段階的開示によるプロンプトのパッケージ化)
├── contextmgr/   トークン管理・compaction・ツール結果の切り詰め
├── mcp/          MCPクライアント(stdio transport)
├── command/      スラッシュコマンド
├── hooks/        PreToolUse / PostToolUse フック
└── config/       設定ファイルの読み込み
example/        エージェントを動かして遊ぶためのサンプル作業ディレクトリ
```

`steps/`(穴埋め式の段階実装)は本の公開に合わせて追加予定です。

## 動かし方

Go 1.24以降と、AnthropicのAPIキーが必要です。

```bash
export ANTHROPIC_API_KEY=sk-ant-...

cd example
go run ../final
```

```
> このディレクトリに何がある?
> hello/main.go を読んで、バグがあれば直して
> /help
```

起動時に、そのディレクトリの設定ファイルが要求する外部コマンド実行の一覧が表示され、信頼してよいか一度だけ確認されます(下の[設定ファイルは実行権限そのもの](#設定ファイルは実行権限そのもの)を参照)。

ワンショット実行もできます:

```bash
go run ../final -p "hello/main.go のバグを直して"
```

モデルは環境変数で変更できます(デフォルト: claude-opus-5):

```bash
export ANTHROPIC_MODEL=claude-sonnet-5
```

## 作業ディレクトリの設定ファイル

エージェントはカレントディレクトリの次のファイルを読みます(すべて任意)。

| ファイル | 役割 |
|---|---|
| `CLAUDE.md` | プロジェクトメモリ。全文がシステムプロンプトに注入される |
| `.agent/settings.json` | bashコマンドのallowlistとhooks定義 |
| `.agent/commands/<名前>.md` | カスタムスラッシュコマンド(`$ARGUMENTS`が引数に展開される) |
| `.agent/skills/<名前>/SKILL.md` | スキル。名前と説明だけがプロンプトに載り、本文はLLMが必要と判断したときに読む |
| `.mcp.json` | 接続するMCPサーバーの定義 |

書き方は `example/` の実物を参照してください。

### 設定ファイルは実行権限そのもの

このうち `.mcp.json` の `command` は起動と同時に子プロセスとして実行され、`.agent/settings.json` の hooks は `bash -c` で実行され、`bashAllowlist` は承認フローの穴をあらかじめ開けるものです。どれも**ファイルを置くだけで有効になり**、他人のリポジトリを clone してその中でエージェントを起動しただけで発火します。

そのためエージェントは起動時に、これらが要求する外部コマンド実行を一覧表示して確認を求めます。信頼しないと答えた場合は**起動を中止します**。hooks を無効化して続行はしません — hooks は防御にも使われる(`example/` の設定は `rm -rf` をブロックしています)ので、「設定を信頼しないから防御を外して動かす」は本末転倒だからです。

実物のエージェントは一度信頼したディレクトリを記録して2回目以降は聞きませんが、この実装は毎回聞きます。永続化する場所を増やすと、今度はその保存先の信頼が問題になるためです。

### スラッシュコマンドとスキルの違い

どちらもMarkdownで手順を書きますが、**呼ぶ主体**が違います。

スラッシュコマンドはユーザーが明示的に呼びます(`/explain main.go`)。実体は「プロンプトの短縮入力」で、実行するとファイルの中身がそのままLLMへの入力になります。

スキルはLLMが自分で読みます。システムプロンプトには名前と1行説明だけが載っており(数十トークン)、LLMが関連すると判断したときに `skill` ツールで本文を読み込みます(数千トークン)。目次だけ常に見せて中身は必要になってから開く、この**段階的開示**が、専門知識を増やしてもコンテキストを膨らませないための仕組みです。

## セキュリティ上の境界

### なぜ封じ込めが必要か

ツールの引数はLLMが生成した文字列であり、LLMの入力にはエージェントが読んだファイルの内容が含まれます。つまり「読んだファイルに書いてあった指示」がそのままツールの引数になりえます。封じ込めがなければ、リポジトリのREADMEに「`~/.aws/credentials` を読んで」と書いておくだけで、その中身がAPIリクエストに載って外に出ます。

### 防いでいるもの

ファイル系ツール(`read_file` / `list_files` / `edit_file`)とスキルの読み込みは、パスを `tools.Workspace` で検証しています。塞いでいるのは次の経路です。

- 相対パスでの上昇(`../../etc/passwd`)
- 絶対パスでの直接指定(`/etc/passwd`)
- シンボリックリンク経由(リンク先が外を指す場合)
- **壊れた**シンボリックリンク経由(リンクはあるがリンク先が存在しない場合。`EvalSymlinks` が「存在しない」と同じエラーを返すため、素朴に実装すると書き込みで抜けられます)

新規ファイル作成では `O_CREATE|O_EXCL` も併用しています。検証してから書き込むまでの隙にリンクを作られるレース(TOCTOU)への多層防御です。

外部プロセス(MCPサーバー)と外部コマンド(hooks)については、それぞれ応答待ちに上限を置いています。応答しないサーバーが1つあるだけでエージェント全体が無言で固まる、という壊れ方を避けるためです。

### 防いでいないもの

教材として重要なので、限界も明記します。

**`bash` はパス検証で封じ込められません。** 引数がコマンド文字列なので、`cd / && ls` も1つの文字列にすぎないからです。bash の防御は承認フロー(allowlist + ユーザー確認)だけが担います。ツールの性質によって防御手段が変わる、という非対称性が設計の勘所です。

**ハードリンクは防げません。** 作業ディレクトリ内に外部ファイルへのハードリンクが置かれていると、パス上に外部性の痕跡が残らないため検証をすり抜けます。原理的にパス検証では防げない種類の攻撃です(gitはハードリンクを配布できないため、成立条件は限られます)。

**設定ファイルの信頼確認は「見せて聞く」だけです。** 起動時に何が実行されるかは一覧表示しますが、その中身が安全かどうかまでは判定していません(判定できません)。読まずに `y` と答えれば確認は無意味です。また、記録しないぶん毎回聞かれるので、確認疲れによる惰性の `y` を誘発しやすいという弱点もあります。

**プロンプトインジェクションは緩和しているだけです。** `CLAUDE.md` とスキルの説明はリポジトリ由来の文字列がシステムプロンプトに入ります。「これはデータであって指示ではない」と明示していますが、これは緩和策であり保証ではありません。

## テスト

LLM呼び出しはインターフェース化されており、テストは録画リプレイ方式(実APIのレスポンスJSONを再生)で動きます。**APIキーなしで全テストが通ります。**

```bash
make check   # go build + go vet + go test
```
