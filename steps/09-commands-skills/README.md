# step 09: スラッシュコマンドとスキル — プロンプトのパッケージ化

よく使う依頼を毎回タイプするのは無駄です。「このファイルを解説して」「コミットメッセージを書いて」——定型のプロンプトには名前を付けて再利用したくなります。

このstepでは、その「プロンプトのパッケージ化」を2方向から実装します。**ユーザーが呼ぶ**スラッシュコマンドと、**LLMが自分で読む**スキルです。同じMarkdownの手順書でも、呼ぶ主体が違うと設計がまるで変わります。

## この章で学ぶこと

- スラッシュコマンド: 実体は「プロンプトの短縮入力」であること
- スキルと段階的開示(progressive disclosure): 目次だけ見せて、本文は必要時に
- 入力の検証は「安全な形だけ通す」——step 04 の原則の再登場

## スラッシュコマンド: LLMに渡る前に展開されるだけ

スラッシュコマンドには2種類あります。組み込みコマンド(`/help`、`/clear`、`/compact`)はLLMを介さずエージェントプログラム自体を操作します。カスタムコマンド(`.agent/commands/<名前>.md`)は、ファイルの中身を展開して**通常のユーザー入力としてLLMに送る**だけです。`$ARGUMENTS` が引数に置き換わります。

「展開されるだけ」という点が肝です。コマンドと言っても、エージェントに新しい能力が生えるわけではありません。それでも定型作業を1語で呼び出せる実用価値は大きい——実物のClaude Codeのカスタムコマンドも同じ仕組みです。

地味に難しいのは「何をコマンドと判定するか」です。「/ で始まる入力」では足りません。ユーザーは `/Users/foo/main.go を読んで` のように**絶対パスから始まる依頼**を普通に書きます。これをコマンド扱いすると「コマンド /Users/foo/main.go は存在しません」と言われ、依頼がLLMに届きません。さらにコマンド名はそのままファイルパスに連結されるので(`.agent/commands/<名前>.md`)、検証なしでは `/../../../etc/passwd` で作業ディレクトリの外を読めてしまいます。対策はどちらも同じで、「コマンド名として安全な文字だけを通す」——step 04 で学んだホワイトリストの原則がここでも効きます。

## スキル: 段階的開示

スキルは「特定の作業のやり方を書いたMarkdownファイル」(`.agent/skills/<名前>/SKILL.md`)です。スラッシュコマンドと似ていますが、起動する主体が違います。

- スラッシュコマンド … ユーザーが明示的に呼ぶ(`/explain main.go`)
- スキル … **LLMが「いま必要だ」と判断して自分で読む**

なぜファイルに切り出すのか。専門知識をすべてシステムプロンプトに書けば確実にLLMに届きますが、使わない知識も毎ターン送られ、コンテキストとコストを食い続けます。逆に必要なときだけ読ませたくても、LLMは存在を知らないものを読もうとはしません。

この矛盾を解くのが**段階的開示(progressive disclosure)**です。

1. システムプロンプトには名前と1行説明だけを載せる(数十トークン)
2. LLMが関連すると判断したら skill ツールで本文を読む(数千トークン)

目次だけ常に見せて、中身は必要になってから開く。人間が分厚いマニュアルを扱うときと同じやり方です。step 05 の CLAUDE.md(常に全文)との対比で、「何を常に載せ、何を必要時に載せるか」という線引きがコンテキスト設計の実践であることが見えてきます。

[skill/skill.go](skill/skill.go)(実装済み)には、final/ のレビューで実際に踏んだ地雷への対策が詰まっています。読んでほしいポイントを2つ挙げます。

- **スキルの読み込みも Workspace を通します。** スキルは「リポジトリに置かれたファイルを読んでプロンプトに載せる」機能で、しかも承認フローを通しません。SKILL.md が外部を指すシンボリックリンクだったら?——レビューでCriticalになった脱出経路です。「ファイルを読む機能を追加するたびに封じ込めを通したか確認する」教訓がここに現れています
- **説明文の長さに上限があります。** 説明はシステムプロンプトに毎ターン載るので、無制限だと「目次だけだから軽い」という前提が崩れます
