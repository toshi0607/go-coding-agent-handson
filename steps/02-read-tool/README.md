# step 02: 最初のツール read_file — エージェントの正体はループである

step 01のチャットに、最初のツール `read_file` を渡します。このstepを終えると、「このファイルに何が書いてある?」と聞くだけで、エージェントが実物を読んで答えるようになります。

そしてここで、本書の核心である**エージェントループ**を実装します。エージェントと呼ばれるソフトウェアの正体は、突き詰めればこのループです。

```
ユーザー入力 → LLM呼び出し → (ツール実行 → 結果を返して再呼び出し)* → 応答
```

## この章で学ぶこと

- ツールとは何か(名前+説明+入力スキーマ+実行本体)
- tool_use / tool_result の往復と、履歴への積み方
- ループの終了条件——「stop_reason を見るだけ」では会話が死ぬ理由

## 前のstepから引き継いだもの

## ツールとは「取扱説明書付きの関数」である

LLMは自分でファイルを読めません。できるのはテキストの生成だけです。ではエージェントはどうやってファイルを読むのか。

答えは役割分担です。こちらがLLMに「ツールの取扱説明書」(名前・説明・入力スキーマ)を渡すと、LLMは必要に応じて「このツールをこの引数で呼びたい」という**リクエスト**(tool_useブロック)を応答に含めてきます。実際にツールを実行するのはこちら側のプログラムで、結果を tool_result としてLLMに送り返します。

つまりLLMは「次に何をするか」を決める頭脳で、手を動かすのはエージェント側です。[tools/tool.go](tools/tool.go) の `Tool` インターフェースがこの4点セット(Name / Description / InputSchema / Run)を表しています。

説明(Description)は人間向けのコメントではなく、**LLMがツール選択の判断に使う実データ**です。「いつ使うべきか」まで書くと選択の精度が上がります。

## ループの終了条件

ループの継続判定を素朴に書くと、こうなります。

```go
if resp.StopReason != "tool_use" { return }  // 罠がある
```

これは2つのケースで壊れます。

**ケース1: max_tokens で切れた応答。** stop_reason は tool_use / end_turn の2値ではありません。出力上限で打ち切られると `max_tokens` になり、このとき**生成途中の tool_use ブロックが応答に残っていることがあります**。Messages APIには「履歴中のすべての tool_use には、直後のメッセージで対応する tool_result を返す」という決まりがあり、対応を欠いた履歴を送ると以降のリクエストはすべて拒否されます。つまり、中断された tool_use を放置してターンを終えると**会話が死にます**。実行しなかった(できなかった)ことを `is_error` 付きの tool_result で返し、必ず対応を閉じてから終える必要があります。

**ケース2: stop_reason が tool_use なのに tool_use ブロックが無い矛盾応答。** このまま続行すると空の user メッセージを送ることになりAPIエラーになります。ここで打ち切るのが安全です。

したがって判定の軸は「stop_reason が何か」ではなく「**未処理の tool_use が残っているか**」です。stop_reason は続行の可否の参考情報に格下げされます。

もう1つの作法が**結果のまとめ方**です。LLMは1回の応答で複数のツールを呼ぶことがあります(並列ツール呼び出し)。その場合も tool_result は**全部まとめて1つの user メッセージ**で返します。

## エラーはループを止めない

`executeTool`(実装済み)を読んでください。ツールが見つからない・実行に失敗した——どの失敗も、エラー文字列を `is_error` 付きの tool_result としてLLMに返し、ループは続行します。

LLMは失敗を読んで次の一手を考えられます。存在しないファイルを読もうとして失敗したら、パスを修正して再挑戦する。これがエージェントの自己修復性の源泉で、「エラーで止めない」は設計判断として意図的なものです。
