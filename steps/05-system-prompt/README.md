# step 05: システムプロンプトとCLAUDE.md — エージェントに環境と規約を教える

ここまでのエージェントは、システムプロンプトなしでLLMを呼んでいました。つまり「あなたが何者で、どこで動いていて、どう振る舞うべきか」を一切伝えていません。それでも動いてはいましたが、たとえば「今日の日付は?」に正しく答えられませんし、勝手に長い前置きを話したりもします。

このstepではシステムプロンプトを設計し、あわせて **CLAUDE.md によるプロジェクトメモリ**を実装します。

## この章で学ぶこと

- システムプロンプトの層構造(役割・環境情報・プロジェクトメモリ)
- 「LLMは実行環境を何も知らない」という当たり前だが忘れやすい事実
- プロジェクト固有の規約をファイルとしてリポジトリに置く、という発想

## 前のstepから引き継いだもの

step 04の解答(権限モデルと封じ込め)は埋まった状態で始まります。今回増えたのは:

- [prompt/prompt.go](prompt/prompt.go) — システムプロンプトの組み立て(課題)
- [agent/agent.go](agent/agent.go) — `Config.SystemPrompt` が増え、`buildParams` がリクエストに載せる(実装済み)

`buildParams` には小さいけれど重要なガードがあります。システムプロンプトが空のときは `System` フィールド自体を送りません。空のテキストブロックはAPIに拒否されるからです(text の最小長は1)。

## システムプロンプトは「役割定義書」

この実装ではシステムプロンプトを3層で構成します。

**1層目: 役割と行動方針(固定)。** 「あなたはターミナルで動くコーディングエージェントです」に続けて、行動方針を数行で書きます。[prompt/prompt.go](prompt/prompt.go) の `basePrompt` を読んでください。「推測でファイルの内容を語らない。必ず read_file で実物を確認してから答える」——この1行があるだけで、LLMがファイル内容をそれらしく捏造する事故が目に見えて減ります。プロンプトは仕様書であり、ここに書く1文は挙動を変える実装の一部です。

**2層目: 環境情報(起動時に注入)。** LLMは自分がどこで動いているか知りません。作業ディレクトリを教えなければツールに渡すパスの推測が外れやすくなり、日付を教えなければ「私の知識は2025年まで……」のような答えが返ります。教えるべきは、作業ディレクトリ・OS・今日の日付といった、起動時にしか分からない値です。

**3層目: プロジェクトメモリ(CLAUDE.md)。** 「このプロジェクトではテストは go test ./... で実行する」「コミットメッセージは日本語」のような規約を、ユーザーが毎回説明するのは無駄です。作業ディレクトリに `CLAUDE.md` というファイルを置いておけば、エージェントが起動時に読んでシステムプロンプトに注入する——つまり**規約をリポジトリに置ける**ようにします。実物のClaude Codeと同じ仕組みです。

CLAUDE.md は「常に従うべき前提」なので全文を毎回載せます。この「何を常に載せるか」という判断は、step 09 のスキル(必要なときだけ読む)と対になります。

## 課題

1. **TODO(step05-1)** [prompt/prompt.go](prompt/prompt.go) — 環境情報の注入
2. **TODO(step05-2)** 同 — CLAUDE.md の読み込みと注入。ファイルが無ければ**何も足さない**(存在しないセクションの見出しでプロンプトを汚さない)

CLAUDE.md を注入するときは、それが何であるか(このプロジェクトで従うべき内容であること)の説明も添えてください。ただのテキスト片を貼っただけでは、LLMはそれをどう扱うべきか分かりません。

## セキュリティの注意

CLAUDE.md はリポジトリ由来のテキストであり、それが「最も信頼度の高い」システムプロンプトに全文入ります。step 04 で見たプロンプトインジェクションの入り口がまた1つ増えた、ということです。他人のリポジトリでエージェントを動かすことの意味は、step 08(設定ファイルの信頼確認)で再び扱います。
