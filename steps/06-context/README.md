# step 06: コンテキスト管理 — 有限の記憶とどう付き合うか

会話履歴・ツール結果・システムプロンプト——LLMに送るものはすべてコンテキストウィンドウという有限の領域に積まれます。放っておくと3つの問題が起きます。

1. 上限を超えてAPIエラーになる(会話が続けられない)
2. 上限に達しなくても、入力トークン分の課金が毎ターン膨らむ
3. 長すぎるコンテキストは応答品質そのものを下げる

対策は2本柱です。**入れる量を減らす**(ツール結果の切り詰め)と、**積んだものを圧縮する**(compaction = 履歴の要約)。このstepでは [contextmgr](contextmgr/) パッケージとしてこの2つを実装します。

## この章で学ぶこと

- トークンをどう「測る」か(自前で数えない。APIの実測値を使う)
- 切り詰め戦略の設計(何を捨て、何を残し、何を伝えるか)
- compaction のタイミング判断——**どこで圧縮するかがすべて**
- Goの文字列とルーン境界(バイトで切ると日本語が壊れる)

## トークンはAPIに数えてもらう

compaction の発動判定にはトークン数が要ります。自前で数えるのは筋が悪い選択です。トークナイザはモデル依存で、正確に再現するのは手間のわりに壊れやすい。

代わりに、**APIレスポンスの usage(実測値)**を使います。毎回のレスポンスには入力・出力のトークン数が正確に入っており、タダで手に入ります。エージェントは直近の値を `lastUsageTokens` に覚えておき、閾値(この実装では8万トークン)を超えたら圧縮する、という判定にします。閾値をモデルの上限(20万〜)よりだいぶ手前に置くのは、上限ギリギリだと要約リクエスト自体が入らなくなるうえ、品質劣化の方が先に来るからです。

## 切り詰め: 何を捨てるかは設計判断

巨大ファイルの read_file や暴走したビルドログは、1件でコンテキストを食い潰します。ツール結果には1件あたりの上限(この実装では2万文字)を設け、超えたら切り詰めます。

この実装の戦略は「先頭を残して後ろを捨てる」です。エラーメッセージやファイルの重要情報は先頭に現れることが多いからですが、これは唯一の正解ではありません。テストログは末尾にこそ結果が出るので「先頭+末尾」もありえますし、実際のエージェントには要約をかけるものもあります。**何をどう捨てるかはエージェント設計の立派な判断ポイント**です。

譲れない点は2つあります。

**切り詰めたことを必ずLLMに伝える。** 黙って切ると、LLMは「全部読めた」と誤解したまま推論を進めます。「N文字で切り詰めた。全体はM文字。続きが必要なら範囲を絞れ」と書き添えれば、LLMは自分でリカバリーできます。

**バイトではなく文字(ルーン)で数える。** Goの文字列はUTF-8のバイト列なので、`s[:20000]` はマルチバイト文字の途中で切れ、壊れたバイト列がAPIに送られます。final/ のレビューで実際に指摘された欠陥で、「N文字で切り詰めた」と告知しながらバイトで切るのは、日本語を扱うツールでは実害のある嘘になります。検証テストは `utf8.ValidString` で壊れを検出します。

## compaction: 要約もまたLLM呼び出しである

圧縮のやり方はシンプルです。履歴の最後に「ここまでの会話を要約して」という依頼を足してLLMに投げ、返ってきた要約だけを新しい履歴にする。[contextmgr/contextmgr.go](contextmgr/contextmgr.go) の `Compact`(実装済み)を読んでください。地味に重要な判断が2つ埋まっています。

- 要約リクエストは**通常のターンと同じ形**(system・tools付き)で送ります。履歴に tool_use が含まれるとき、tools を伴わないリクエストはAPIに拒否されるからです。ただし tools を渡すとLLMがツール呼び出しで応えかねないので、`tool_choice: none` でテキストを強制します
- 要約は非可逆圧縮です。一度失った詳細は戻りません

そして最大の判断が「**いつ圧縮するか**」です。圧縮できるのは**ターンの境界だけ**。ツールループの途中で履歴を要約すると、tool_use と tool_result の対応が要約に飲み込まれて壊れ、以降のリクエストがすべて拒否されます。皮肉なことに、コンテキストが逼迫するのはたいてい長いツールループの最中なのですが、それでも境界まで待つのが正解です。検証テストには「閾値を極端に下げてもループ中は圧縮しない」という不変条件テストがあります。
