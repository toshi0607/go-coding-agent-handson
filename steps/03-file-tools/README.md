# step 03: list_files と edit_file — コードを書けるエージェントの完成

ツールを2つ足します。ディレクトリを一覧する `list_files` と、ファイルを編集する `edit_file` です。

このstepを終えると、「hello/main.go のバグを直して」という依頼が通ります。探して(list_files)、読んで(read_file)、直す(edit_file)。コーディングエージェントの基本動作が、ここで一通り揃います。

## この章で学ぶこと

- ツールセットの直交性——少数の直交するツールの組み合わせで仕事が成立すること
- old/new置換方式の編集と、その設計理由(なぜ行番号指定ではないのか)
- エラーメッセージを「LLMへのフィードバック」として設計すること

## 前のstepから引き継いだもの

step 02の解答(read_file の実装、エージェントループ)は埋まった状態で始まります。エージェントループ側は今回**一切変更しません**。ツールを増やしても、ループは `Tool` インターフェースしか見ていないので、そのまま動きます。最初にインターフェースを切っておいた効能です。

## ツールセットの直交性

「探す」「読む」「書く」はそれぞれ独立した1機能で、重複がありません。この直交性が大事です。

LLMはツールの説明を読んで使い分けを判断します。機能が重複したツールが並んでいると、どちらを使うべきかの判断が不安定になります。逆に直交していれば、組み合わせは自由です。「まず list_files で全体を把握 → 関係しそうなファイルを read_file → edit_file で修正」という段取りは、こちらが教えなくてもLLMが自分で組み立てます。

[tools/list_files.go](tools/list_files.go)(実装済み)には実務的な配慮が2つ入っています。`.git` などの隠しディレクトリのスキップと、エントリ数の上限です。巨大リポジトリで数万ファイルの一覧を返すと、それだけでコンテキストが埋まってしまいます(コンテキストの話は step 06 で本格的に扱います)。

## なぜ old/new 置換方式なのか

`edit_file` の編集方式は「old_str を new_str に置き換える」です。これは現実のコーディングエージェントでも主流の方式で、理由があります。

候補は他にもあります。たとえば「N行目からM行目を書き換える」(行番号指定)や「ファイル全体を書き直す」(全置換)です。しかしLLMは行番号の計算を間違えやすく、全置換は長いファイルで出力トークンを浪費するうえ、書き直しの過程で無関係な箇所を壊すことがあります。一方、「いま read_file で見た内容をそのまま引用する」のはLLMの得意技です。old/new置換はこの得意技に寄せた設計です。

もう1つの判断が**一意性の要求**です。old_str がファイル内に複数回出現する場合、この実装はエラーにします。どこを置き換えるか曖昧なまま書き換えるより、「前後の文脈を含めて一意にしてください」とLLMに突き返す方が安全だからです。エラーメッセージがそのまま「次にどうすればいいか」の指示になっていることに注目してください。

| 条件 | 動作 |
|---|---|
| old_str が空 かつ ファイルが無い | 新規作成(親ディレクトリごと) |
| old_str が空 かつ ファイルが有る | エラー(黙って上書きしない) |
| old_str が見つからない(0回) | エラー |
| old_str が複数回 | エラー(曖昧さを拒否) |
| ちょうど1回 | 置き換えて保存 |
